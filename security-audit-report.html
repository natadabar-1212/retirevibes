● Overall Risk Level: LOW — appropriate for prototype stage

Executive Summary

RetireVibes is a static HTML/CSS/JS web app with no server-side backend. This significantly limits the attack surface — there is no database, no authentication system, and no server processing of user input. All data storage lives in the visitor's own browser via localStorage.

The audit reviewed all 15 HTML files, shared JS/CSS, and the affiliate link inventory. Seven findings were identified. None are exploitable by a remote attacker without physical access to the victim's browser. The two Medium-severity findings should be addressed before the real build launches; the Low and Info findings are recommended improvements.

Findings

F-01 MEDIUM
Missing referenced JS files
results-page-mockup.html — lines 1415–1418
Problem

The results page loads three JavaScript files that do not exist in the project: destinations-data.js, results-matcher.js, and magic-link.js. The page also loads the EmailJS SDK from jsDelivr, which requires magic-link.js for initialization.

Risk

Missing script files cause silent failures or console errors when deployed. More importantly, magic-link.js is where the EmailJS public key and service/template IDs will live. If that file is committed to a public GitHub repo without domain restrictions configured first, anyone who finds the key could send unauthorized emails through your account — exhausting your monthly quota or getting your account flagged.

How to Fix

Create the three missing files. When writing magic-link.js, restrict the EmailJS service to your domain before pushing the key to GitHub. Do this in the EmailJS dashboard under Settings → Allowed Origins.

// In EmailJS dashboard: Settings → Allowed Origins → https://retirevibes.com // In magic-link.js: emailjs.init({ publicKey: 'YOUR_PUBLIC_KEY', blockHeadless: true, // blocks bots and scrapers });
F-02 MEDIUM
innerHTML used with localStorage data (self-XSS)
my-retirevibes.html — lines 811, 825, 842–866, 886–899, 931
Problem

The My RetireVibes page reads quiz match data from localStorage (key: rv_quiz_matches) and destination names from rv_saved, then inserts them directly into the DOM via innerHTML without any sanitization. Affected values include the vibe label, profile paragraphs, match card name/photo/flag/tagline, and saved destination names.

Risk

This is a self-XSS pattern: an attacker would need physical access to the victim's browser to modify localStorage and trigger the injection. A remote attacker cannot exploit this directly. However, if any other vulnerability is introduced that can write to localStorage (e.g., a future URL parameter that isn't validated), this escalates immediately to a stored XSS. It is also a fragile pattern that grows more dangerous as the codebase evolves.

How to Fix

Replace innerHTML with textContent for all text content. For elements that need italic styling (like the vibe name), use createElement and appendChild.

// ❌ Before (vulnerable): nameEl.innerHTML = parts[1] + '<em>' + parts[2] + '</em>'; // ✅ After (safe): nameEl.textContent = parts[1]; const em = document.createElement('em'); em.textContent = parts[2]; nameEl.appendChild(em); // For profile paragraphs: // ❌ Before: profileEl.innerHTML = lines.map(l => '<p>' + l + '</p>').join(''); // ✅ After: lines.forEach(l => { const p = document.createElement('p'); p.textContent = l; profileEl.appendChild(p); });
F-03 LOW
innerHTML used with dynamic strings (hardcoded data)
find-an-advisor.html (line 883), results-page-mockup.html (line 1159), destination-coming-soon.html (line 257)
Problem

Three pages use innerHTML to inject a dynamic string with an italic accent — the advisor name in the contact modal, the destination name in the save modal title, and the destination name in the coming-soon headline. In all three cases, the source values are currently hardcoded (advisor names from static HTML attributes; destination names from a JS dictionary keyed on URL param).

Risk

Low risk today because the values are not user-controlled. However, the pattern is fragile — if the data source ever changes (e.g., destination names come from an API or user input), an XSS vulnerability would be silently introduced.

How to Fix

Same createElement approach as F-02. Three small changes across three files.

// ❌ Before: titleEl.innerHTML = 'Connect with <em>' + advisorName + '</em>.'; // ✅ After: titleEl.textContent = 'Connect with '; const em = document.createElement('em'); em.textContent = advisorName; titleEl.appendChild(em); titleEl.appendChild(document.createTextNode('.'));
F-04 LOW
External links missing rel="noreferrer"
scouting-trip.html, browse-homes-international.html, browse-homes-domestic.html, destination pages
Problem

All external affiliate links (Booking.com, Expedia, Idealista, Zillow, etc.) use rel="noopener" but are missing rel="noreferrer". The noopener attribute is present and correct — it prevents the linked page from accessing window.opener. But without noreferrer, the browser sends a Referer HTTP header to the destination site revealing exactly which RetireVibes page the user clicked from.

Risk

Affiliate partners and their analytics will see your internal page URLs in referrer logs — exposing your site structure and traffic patterns. This is a privacy and competitive information concern more than a direct security risk.

How to Fix

A simple find-and-replace across all HTML files — takes under 5 minutes.

Find: rel="noopener" Replace: rel="noopener noreferrer"
F-05 LOW
CDN script loaded without Subresource Integrity hash
results-page-mockup.html — line 1417
Problem

The EmailJS browser SDK is loaded from jsDelivr without an integrity attribute. Current tag:

<script src="https://cdn.jsdelivr.net/npm/@emailjs/browser@4/dist/email.min.js"></script>
Risk

If jsDelivr (or the EmailJS package on npm) were ever compromised and the CDN served a malicious version of the script, it would run with full page access — including localStorage, form inputs, and the ability to exfiltrate email addresses submitted through the save modal. CDN compromise is rare but has happened (see: Polyfill.io incident, June 2024, which affected 100,000+ websites).

How to Fix

Generate an SRI hash for the exact file version and add it as the integrity attribute. You can generate one at srihash.org — just paste the CDN URL and it gives you the tag.

# Or generate locally: curl -s https://cdn.jsdelivr.net/npm/@emailjs/browser@4/dist/email.min.js \ | openssl dgst -sha384 -binary | openssl base64 -A # Then use it in the script tag: <script src="https://cdn.jsdelivr.net/npm/@emailjs/browser@4/dist/email.min.js" integrity="sha384-PASTE_HASH_HERE" crossorigin="anonymous"></script>
F-06 INFO
No Content Security Policy defined
All pages
Problem

No Content Security Policy (CSP) is set on any page — neither as an HTTP response header nor as a <meta> tag. CSP is a browser feature that restricts which scripts, styles, fonts, and other resources can load.

Risk

Without a CSP, if an XSS vulnerability is ever introduced, the attacker has no browser-level restrictions on what they can do. CSP is defense-in-depth — it does not replace fixing root causes (F-02, F-03), but it limits the blast radius if something goes wrong. Note: GitHub Pages doesn't support HTTP headers, so the <meta> approach is your primary option.

How to Fix

Add a CSP meta tag to each page's <head>. Start permissive — tighten as the build grows. Add this to shared.css's companion or bake it into a template.

<meta http-equiv="Content-Security-Policy" content=" default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' https://fonts.googleapis.com 'unsafe-inline'; font-src https://fonts.gstatic.com; img-src 'self' https://images.unsplash.com data:; connect-src 'self' https://api.emailjs.com; ">
F-07 INFO
EmailJS public key will be visible in client-side JS
magic-link.js (not yet created)
Problem

When magic-link.js is written to initialize EmailJS, it will contain your public key, service ID, and template ID — all visible in page source and in the public GitHub repo.

Risk

This is expected and by design for EmailJS — their SDK is built to be used client-side. However, an unrestricted key can be discovered by scrapers and used to send unauthorized emails through your account, potentially exhausting your monthly quota or getting your account flagged for spam.

How to Fix

Three steps when setting up EmailJS:

  1. Restrict allowed origins to retirevibes.com only (EmailJS dashboard → Settings → Allowed Origins)
  2. Enable "Block headless browsers" in EmailJS settings to stop bots
  3. Add a comment in magic-link.js noting the key is intentionally public but domain-restricted

What's Not a Concern

For completeness — these common vulnerability classes do not apply to RetireVibes in its current static form:

  • SQL injection — no database, no server-side queries
  • Server-Side Request Forgery (SSRF) — no server
  • Authentication bypass — no login system exists
  • Session hijacking — no sessions or cookies set by the app
  • Command injection — no server-side code execution
  • CSRF — no state-changing server endpoints
  • URL parameter injection — all pages that read URL params either validate against a whitelist (destination-coming-soon.html, find-an-advisor.html) or use values only for UI filtering, never for unvalidated DOM injection

GitHub Repository Checklist

Separately from the code, verify these settings in your GitHub repo:

  • .gitignore is present and excludes any future .env files, node_modules, and OS files like .DS_Store
  • No API keys or credentials exist in any commit — including old commits. Use git log -p | grep -i "api_key\|secret\|password" to check history
  • Enable GitHub Secret Scanning (Settings → Security → Secret scanning) — it will alert you if a key is accidentally committed
  • Enable Dependabot alerts if you add npm dependencies in the real build
  • Consider branch protection on main to require review before merging

Recommended Fix Order

Prioritized by impact and effort — all seven findings can be addressed in a single focused session:

  1. F-01 — Create the missing JS files; set up EmailJS with domain restriction before pushing the key
  2. F-02 — Refactor my-retirevibes.html to use textContent and createElement instead of innerHTML
  3. F-03 — Fix the three innerHTML instances in find-an-advisor.html, results-page-mockup.html, and destination-coming-soon.html — do this at the same time as F-02
  4. F-04 — Global find-and-replace: rel="noopener" → rel="noopener noreferrer"
  5. F-05 — Generate the SRI hash for EmailJS and add it to the script tag
  6. F-06 — Add the CSP meta tag; iterate as the build grows
